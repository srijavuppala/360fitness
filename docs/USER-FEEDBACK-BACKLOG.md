# 360 Fitness — user feedback and use cases

Captured October 10, 2026 from the supplied checklist. These are development requirements, not completed features. The screenshot shows 13 unchecked items and a `1/14 done` heading; the completed item is not visible and has not been guessed. Priorities below are proposed implementation order.

| ID / priority | Use case and current status | Frontend work | Backend work | Database work | Acceptance criterion |
| --- | --- | --- | --- | --- | --- |
| U01 · P1 | Suggest groceries within a budget. Budget is currently a preference, not a priced recommendation engine. | Offer budget ranges, affordable swaps and an editable suggested basket. | Rank suggestions using available price data; identify estimates and unavailable prices. | Budget currency/period, dated price source, basket items and accepted swaps. | A user can accept or change suggestions; estimated prices never appear as verified totals. |
| U02 · P1 | Make meal check-in suggestive. Meal logging exists; suggestion-first check-in needs design. | Compact meal cards with horizontal browse/swipe, usual meals and an explicit manual-entry button. | Return relevant suggestions from consented profile and confirmed history. | Store suggested/accepted meal IDs separately from confirmed logs. | Swiping never records food as eaten; explicit confirmation creates one entry. |
| U03 · P1 | Replace waist measurement in onboarding with height. Requested change. | Add optional height with cm/ft-in controls; remove waist from the onboarding choices. | Validate and normalize height; preserve compatibility with older profile versions. | Version height schema; keep historical waist data without relabeling it as height. | Existing profiles reopen safely; height round-trips correctly across units and cloud restore. |
| U04 · P0 | Prioritize manual logs, swipe actions and separate users. Local storage currently has one app-state record. | Manual entry first; edit/delete with undo; visible alternatives to gestures; account-switch/loading states. | Authenticate ownership, validate events, deduplicate retries and reconcile revisions. | UID-scoped local state/outbox and owner-scoped cloud events; explicit guest-data import. | A logs a meal, signs out, then B signs in: B cannot see or upload A's data. Offline retries create no duplicates. |
| U05 · P0 | Fix meal logging reporting “We don't have the log”. User-reported; reproduction pending. | Show save success only after persistence; expose pending/error states and retry. | Trace event creation/read paths with redacted diagnostics; standardize IDs and dates. | One canonical event identity, local date/time zone and revision. | Save, reopen and query the same meal on iOS/Android; no false missing-log response after a successful save. |
| U06 · P0 | Show logged meals on the main page. Today screen exists; reported missing-meal behavior needs verification. | Put today's confirmed meals and quick actions on Today; expand details on demand. | Use the same day query as history and check-in; invalidate/refetch after writes. | Derive summary from canonical events rather than maintaining independent logs. | Add/edit/delete is reflected in Today and history with matching portions and totals. |
| U07 · P0 | Fix Dictate opening the keyboard. Native speech entry exists; device reproduction needed. | Dismiss keyboard for recording; listening/stop/review states; separate typed fallback. | No new AI endpoint required for OS dictation; enforce limits if server extraction follows. | Save only user-approved text; no raw-audio retention by default. | On signed iOS/Android builds, Dictate starts the permission/recording flow; denial or unavailable service gives a clear fallback. The unexplained note “that silly port” remains unresolved. |
| U08 · P1 | Allow multiple answers where appropriate. Some survey fields already support multi-select. | Review each question's cardinality; checkboxes/chips for multi-select; exclusive “none” behavior. | Validate enum arrays, bounds and mutually exclusive choices. | Version scalar-to-array changes and migrate existing values. | Users can select, deselect, save and restore multiple allowed values without silently losing choices. |
| U09 · Needs definition | Add a 30-day option. The checklist does not identify the feature. | Proposed interpretation: 7/30-day progress filter; confirm whether this means progress, meal planning or a challenge. | Query the selected date range after scope is decided. | Prefer query/derived summaries to duplicated 30-day records. | Definition of the option and date boundaries agreed before implementation; missing days never shown as zero intake. |
| U10 · Needs definition | Finish Google setup. Email/password account UI exists; Google sign-in and Play distribution are different tasks. | If sign-in: Google entry, cancel/retry/link-account flow. If store: release assets and listing. | Configure identity provider/token verification for sign-in, or EAS submission for Play. | Link provider identity to existing UID; avoid duplicate users. Store service credentials stay outside the repo. | Decide sign-in, Play Store, or both; verify chosen path on physical devices before calling complete. |
| U11 · P2 | Connect wearables. Current onboarding records interest only. | Connection consent, permission status, source attribution and disconnect. | Evaluate HealthKit/Health Connect/provider APIs; incremental sync and deduplication. | Provider/source IDs, sample timestamps, import cursor, consent/revocation records. | Repeated imports do not duplicate activity; revoked permission stops reads; manual and imported records reconcile. |
| U12 · P1 | Collect accessibility ideas and test them. | Audit VoiceOver/TalkBack, text scaling, contrast, focus, touch targets and reduced motion; keep buttons for swipe actions. | Return actionable, accessible errors rather than generic failures. | Persist accessibility preferences only if needed; avoid collecting disability labels. | Core onboarding/logging/review works using screen readers and larger text on both platforms. |
| U13 · P1 | Map the end-to-end app flow. Architecture exists; full journey validation remains. | Welcome → account/guest → onboarding → Today → meal/manual/photo/voice review → confirm → history/prep → settings. | Specify authentication, validation, analysis, confirmation, sync and deletion transitions. | Distinguish drafts, confirmed events, summaries and opt-in memory with lifecycle rules. | Journey diagram includes offline, cancellation, expired-session, denied-permission, retry and deletion branches; each has a device test. |

## Delivery sequence

1. Reproduce U05/U06/U07 on signed phone builds; implement U04 account isolation before a shared-device pilot.
2. Deliver U03/U08 onboarding changes and U02 meal suggestions; complete U12/U13 alongside those screens.
3. Define U09/U10, then implement budget recommendations and wearable integrations with verified providers.

Use one GitHub PR per coherent fix, referencing its U-ID. Include frontend behavior, service contract, migration/rules impact and acceptance evidence. These requirements supplement [the full feature audit](FEATURE-COVERAGE-AUDIT.md) and [the multi-user testing guide](expo-and-app-users.md).
